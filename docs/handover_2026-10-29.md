   and body, log line and level, rows in the preview store and queue tables);

4. a proposal (not built) so that every 2xx path leaves a trace in Slack or HubSpot.

**Facts already established (do not re-derive):**

- `server.py` `_dispatch`: a handler returns `(data, status)`; the envelope is `ok = status == 200`. A `RestHTTPError`
  4xx becomes 422, 5xx becomes 502, any other exception becomes 500 `intake failed`. So "2xx to HubSpot" means the
  handler returned 200.
- **queue_timeline** (`actions/queue_timeline/web.py`): `QUEUE_MODE=off` returns 503. **`QUEUE_MODE` UNSET means
  `dry_run`** (`worker.mode()`), so the web side accepts the job with 200 and the worker only previews it: the job
  ends `dry_done`, NOTHING is committed, and the only trace is the queue DIGEST (`post_digest`: every 30 minutes
  or when the queue drains, lines marked "DRY RUN"). No per-deal Slack, no HubSpot write. This is the strongest
  match for the symptoms and must be checked first (`QUEUE_MODE` in the droplet's `.env`).
- `already_queued` (an identical live job or a done job holds the idempotency key) returns 200 with only an INFO
  log: no Slack, no HubSpot write. An active job for the child returns 409 plus a Slack notice.
- A newly queued job returns 200 and nothing else; the work is async. A job stays `queued` silently if the worker
  unit is not running, the queue is paused (`run_once` just returns False; a Slack notice exists only when the
  breaker or pause trips), the daily cap is reached (one Slack notice per day, else `STANDS DOWN` WARNING log), or
  `QUEUE_MODE` becomes off (`_run` puts the job back to `queued`, "queue is off"). A job left `running` by a crash
  is resumed by READ-BACK only at worker start (`recover_running`); nothing alarms on a job that sits `queued` or
  `running` for hours (confirm there is no stale-job alert: none found so far).
- Worker outcomes: `fail()` posts Slack and (since `e5f836a`) writes `needs_attention`, but ONLY if the job
  payload carries `dealId` (a job queued before that commit, or from a body with no deal id, writes nothing to
  HubSpot). `hold()` posts the Approve message. `expire_held()` posts a Slack notice. `QUEUE_ALLOWED_INSTITUTIONS`
  empty means none allowed: in `auto` the plan is HELD (Slack Approve message); in `dry_run` it only adds a reason
  to the digest line.
- **create_timeline** (`actions/create_timeline/web.py`): an active chain for the child returns 409 + Slack; an
  existing plan returns 409 + Slack (`_refuse`); a Slack post failure for plan 1 returns 502 and stops the chain;
  `maintenance.expire_stale_chains()` runs on every request.
- **plan_preview** (`actions/plan_write/web.py`): validation failure = 422 (now Slack + HubSpot). A success returns
  200 even if the Slack Approve post FAILS (`slack_posted: false`, "never changes the HTTP status"): the preview
  row stays `pending`, nothing in Slack, nothing in HubSpot. A preview that is never approved expires after
  `PREVIEW_TTL_HOURS` (default 24) silently (expiry is applied lazily on access; no sweeper found for the direct
  route). A failure to STORE the preview is only a WARNING log. These are the direct-route candidates for the 12.
- Storage: default `var/preview_store.sqlite3` (override `PREVIEW_STORE_PATH`). Tables: `previews` (preview_id,
  plan_body, child_id, version, created_at, status, site_code, institution_id, pricing_group_id,
  monthly_estimate, old_plan_id, replace_old_plan, chain_id, chain_index, job_id, job_index, deal_id), `chains`,
  `jobs` (job_id, job_key, child_id, payload, segments, next_index, status, detail, preview_id, digest_sent,
  created_at, updated_at), `queue_state` (key, value), `delete_log`. Job statuses: queued, running, done,
  dry_done, held, failed, cancelled. Unit names known: `famly-queue-worker`, `famly-onboard-worker`; the gunicorn
  unit name is NOT in the repo (find it with `systemctl list-units --type=service | grep -i -E "famly|gunicorn"`).
- Logging reaches journald only through `core.logging_setup.configure_logging` (INFO, stderr); gunicorn needed a
  restart after 2026-10-19 to load it.

## 4. Decisions and facts delivered but NOT built (awaiting Drew)

a. **Weekday `none` in plan derivation.** Drew confirms `none` means the child does not attend that day, so plans
   should be created. Today `hubspot_flatten.build_session_bookings` (and the `booked_days` list that feeds add-on
   products, about line 650) treat any non-empty value as booked and `resolve_session` rejects `none` as a hard
   error (`plan_rejected:session_catalogue:day_slot_invalid` on every route). Proposal: one helper `_day_value`
   returning "" for `none`, used at both places; the audit imports the same constant. Add-ons then land only on
   attended days; all five none/empty is rejected as before (`no_bookings`). Open: what the workflow body sends
   for an unattended day (literal `none`, empty or omitted) is not in the repo; check stored queue payloads
   (`json_type(payload,'$.monday')` on `jobs`) and the workflow's webhook history.
b. **Partial advanced-fee / funding groups.** Facts only, no design: the rule is `engine.parse_request.period()`
   (`engine.py:223-243`, queue and chain routes only): funding = `has_funding` + `funding_start` + `funding_end`
   (+ `funding_entitlement` for a funded plan); advanced = `has_advanced_fee` + `advanced_start` + `advanced_end` +
   `advanced_discount`. Ignoring either group can only OVERCHARGE the parent (funding removes funded hours and
   the add-on/slot-9 treatment; advanced removes the slot-10 weekly percent discount). The queue's fully-funded
   zero-estimate safety net would not fire. The Approve message would not show an omitted group (heading says
   "base"; a local warning would have to be added in `prepare_preview`; queue plans auto-commit with no Approve
   message). `status_sync.mark_plan_created` clears the note on success, so a warning code on the deal would need
   a note parameter plus a `previews` column to carry it.
