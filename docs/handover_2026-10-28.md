## 2. Facts learned live (do not re-derive)

- A HUBSPOT reference set at contact create is stored and found by `contacts.listByExternalSystemReference`; siblings may share one id (filter by child); a second HUBSPOT reference on one contact is refused (one per system); adding the **first** one through the full contacts update is accepted, with other fields unchanged (not built).
- `contacts.update(records: ...)` merges per key (proven for adding a key; **not proven for replacing an empty value**, see section 4).
- `billPayers.addInvoiceRecipients({relationId = the contact id, billPayerId})` works; a repeat add is HTTP 400, errorCode 1675864914, with the pair in `extensions.payload.existingEntries` (treated as success). Recipient reads lag.
- `billPayers.create` at share 0.0 is rejected (HTTP 400); the pipeline creates at 1.0 only.
- Parent app access is a role on the contact (Parent, Parent limited, Family) and needs a login; pipeline contacts are created with `roles: []`. A recipient alone probably does not give app access (inferred, not proven). Not built.
- Famly returns a RELATION record for every contact; empty value means unset.
