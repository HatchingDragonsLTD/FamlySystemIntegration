## Part 3. Why the full contacts update was refused, and what else can set a reference

**The error class is not known.** The probe's `send` kept `type(exc).__name__` in memory and
printed only the boolean `4_reference_update_accepted: False`. No terminal output from that run was
kept, so the class (GraphQLError or GraphQLHTTPError), the HTTP status and any `extensions.code`
cannot be named without sending the write again, which was not done. The next probe must print the
exception type, the HTTP status and `errors[].extensions.code` (never the message).

**Most likely cause, from the live schema (an inference, not an observation).** Step 4 sent TWO
references with the same system (`HUBSPOT`, the first echoed and a second added). The schema says of
`ContactUpdate.externalSystemsReferences`: "one per system" and "When provided, replaces all of the
contact's references: an empty list removes them. Omit the field, or pass null, to leave them
unchanged." A second `HUBSPOT` entry breaks "one per system". So a contact can hold exactly one
HUBSPOT reference, and what step 4 tried (a second HUBSPOT id on the same contact) is not a thing the
API allows. Weaker candidates: the full update also replaces name, phones, records and roles
(`roles: []` was sent, the contact had none), and "Setting them requires permission to edit the basic
information of children at the child's site" (less likely: the create with a reference had worked).

**Is there a narrower way to set or add references on an existing contact? No.**
- Public API: `ContactsMutation` has only `create` and `update`. `update` takes `contacts` (the full
  `ContactUpdate`, "updates all fields"), `forceAccountsSync`, and the single-field arguments `names`,
  `records`, `roles`, `emails`, `phones`, `emergencyContacts`. There is NO references argument.
  `externalSystemsReferences` exists only on `ContactInput` (create) and `ContactUpdate` (full).
- Internal API: `childContacts` (`ContactsMutation`) has `create` (`ContactInvitationInput`, no
  reference field), `update` (the same eight arguments; its `ContactUpdate` has no reference field),
  `updateRole`, `copyContacts` and `resendVerifiedInvitation`. No reference field on the internal
  `Contact`, `ContactInvitationInput` or `ContactUpdate`. `copyContacts` duplicates contacts onto
  another child ("does not do anything clever"), so it is not a way to set a reference.
- So the only way to put a reference on an existing contact is the public full `contacts:` update,
  which replaces name, phones, records and roles from the input. What it does with omitted OPTIONAL
  fields (email, address, emergencyContact) is not stated (the to-do 5 probe).

2. Read it back and keep a snapshot in memory: name, email, phones, address, all five record keys,

3. ONE full `contacts:` update, write 2, echoing every readable field exactly and setting

4. Read it back and print booleans: reference present, system returned, and each of name, email,
   phones, address, records, emergencyContact unchanged. If it is refused, print the exception type,

## Part 6. Bill payer to contact link

**How Famly connects them.** The link is an **invoice recipient**: a pair (contact, bill payer).
Public API: `BillPayer.invoiceRecipients -> [InvoiceRecipient {relationId, contactId, billPayerId,
name, email}]` (read), `billPayers.addInvoiceRecipients(invoiceRecipients: [InvoiceRecipientInput!]!)
-> [InvoiceRecipient!]!` ("An invoice recipient is a link between a relation/contact and a bill
payer"), `billPayers.deleteInvoiceRecipients([{relationId!, billPayerId!}])`, and
`BillPayerInput.invoiceRecipients` at create. `InvoiceRecipientInput` = {relationId, billPayerId,
childId, name, email}: `relationId` for an existing contact (and `billPayerId` always, for an
existing payer); `childId`, `name` and `email` instead to create a recipient without an existing
contact. The public `Contact` does not expose a `relationId`, but on every recipient read
(366 of 366: 111 at HDCITY, 135 at HDCW, 120 at HDWEST, live payers' recipients) `relationId` equals
`contactId`, so the public contact id is the relation id.

**Does the pipeline do it today? No.** There is no `invoiceRecipients`, `addInvoiceRecipients` or
`relationId` anywhere in `actions/onboard*`. The bill payer stage (`actions/onboard/bill_payer_writes.py`)
sends `billPayers.create` (name, email, phone if it normalises, the child inline at share 1.0, no
address, no externalId, no invoice recipients) or `addChildren`, and nothing else. The contacts stage
creates parents with `roles: []`. So a pipeline-made payer has no recipient, and the status entries
of 2026-10-23 say the same.

**Live counts** (read-only, counts only; the cap was 120 children and 60 qualified, so every child
carrying a HUBSPOT deal reference was examined; a payer counts for a child only at a share above 0):

| site | onboarded children | with a live payer | distinct payers | payer has a recipient | payer has none |
|---|---|---|---|---|---|
| HDCITY | 18 | 2 | 2 | 0 | 2 |
| HDCW | 17 | 4 | 4 | 2 | 2 |
| HDWEST | 25 | 5 | 4 | 0 | 4 |
| total | 60 | 11 | 10 | 2 | 8 |

At HDCW one of the two recipients is a contact on the child in question and one links only a contact
that is not on this child. 49 of the 60 children have no live payer at all: the bill payer stage has
not run live yet, so the payers that do exist for these children were made by hand, and 8 of those 10
have no recipient. (Across the three sites there are 366 recipients in all; the number of payers they
belong to was not counted.)

**The mutation.** `billPayers.addInvoiceRecipients(invoiceRecipients: [{relationId: <contact id>,
billPayerId: <bill payer id>}]) -> [InvoiceRecipient]`. It ADDS: the description is "Add the given
invoice recipients", and removal is the separate `deleteInvoiceRecipients`, so it is neither a merge
nor a replace of the payer's set. The schema does not say whether adding a pair that already exists
errors or is a no-op, so the stage must read first and never send a pair that is already there.
Alternative at create: put `invoiceRecipients: [{relationId}]` inside `billPayers.create` (one
request; the contact already exists because the contacts stage runs first).

**One caution on "the parent sees invoices in the parent app".** The schema defines only who is an
invoice recipient. Whether the app shows invoices to a recipient also depends on that contact having a
login (a role such as Parent), and the pipeline creates contacts with `roles: []` (app access is not
built). The schema cannot answer whether a recipient without a login sees anything, so the link
alone should not be assumed to give the parent app access.

**Where it fits.** A third step of `bill_payer_writes.run_stage`, after the create or attach has
been read back, for the bill payer contact only (not the other parents):
- Plan time: add `invoiceRecipients { relationId billPayerId }` to `bill_payers_scan.graphql` (the
  scan already reads payers; no extra request). Plan field `billPayer.recipient`: `would_link`
  (payer and contact known, no recipient for that contact), `linked`, or `contact_missing`. It is in
  the plan hash.
- Write: one `addInvoiceRecipients` per payer, sent once, never retried, with the relation id taken
  from the contact the stage just matched or created (`locate_contact`) and the payer id from the
  create or attach. Not for child-only stages.
- Settle: a clean answer is read back with the payer scan and `LOOKUP_RETRY_WAITS`; an unknown outcome
  is settled by the same read (the pair present = done), never by sending again. Not present after the
  retries = flag `bill_payer_recipient_not_linked` (To check), not a stop, like the relation write.
- Gate A and the status block: a new write in `plan_status.planned_writes` ("1 bill payer contact
  link") and three new sentences in `messages.state`: will link the bill payer contact as invoice
  recipient, already linked, flagged.
- The unresolved-outcome guard works as for the payer: an earlier unconfirmed link with no pair
  showing stops a second send.

**A safe capped probe (not run).** Test child and the existing `probe-bill-payers` write machinery:

## Part 7. HubSpot deal writes

- **Module:** `core/hubspot.py`, class `HubSpotDealWriter(HubSpotClient)`, method
  `write_deal_properties`. It is reached only through `actions/onboard/hubspot_sync.py` (`Syncer`,
  one property per request) and `actions/onboard/worker.py` (`_write_allocated_urn`, the URN).
  `HubSpotClient` itself has no write path.
- **Properties it may write** (`WRITABLE_DEAL_PROPERTIES`; any other name raises `ValueError` before
  anything is sent): `child_urn` (only to a deal that has none, before the Famly child is created),
  `famly_childid`, `famly_sync_status`, `famly_sync_note`, `famly_sync_gaps`, `end_date` (only when
  empty and defaulted, after the Famly write, never overwritten).
- **HTTP:** `PATCH https://api.hubapi.com/crm/v3/objects/deals/{deal_id}` with body
  `{"properties": {name: str(value)}}`. Retried on 429 and 5xx (up to 5 attempts, backoff) because the
  same PATCH is idempotent. The deal property listing is a GET of `/crm/v3/properties/deals`.
- **Token:** `HUBSPOT_TOKEN`, the private app "Famly_Server_Key" (never printed). By the endpoints the
  class calls, it needs `crm.objects.deals.write` for the PATCH, and reads for deals, contacts and
  quotes (`crm.objects.deals.read`, `crm.objects.contacts.read`, `crm.objects.quotes.read`),
  `crm.schemas.deals.read` for the property listing, and the pipelines and association-label reads.
  These come from the HubSpot API, not from the token: the scopes actually granted to the app are
  visible only in HubSpot (Settings, Integrations, Private apps), and were not checked here.
- **famly_plan_uploaded:** mentioned only in `docs/famly_onboarding_pipeline_design.md`; nothing in the
  code reads or writes it, and its HubSpot type is not recorded in the repo. The smallest change to
  write it from the server later, with no second writer:
  1. add `PLAN_UPLOADED_PROPERTY = "famly_plan_uploaded"` to `core/hubspot.py` and put it in
     `WRITABLE_DEAL_PROPERTIES`. `hubspot_sync.CHECKED` is built from that set, so the existing
     pre-flight already warns `missing:famly_plan_uploaded` if the property does not exist;
  2. have the plan-creating code call the existing `Syncer.write` (or `HubSpotDealWriter.write_deal_properties`)
     with the string `"true"` when a plan was created and `"false"` when not. Pass the strings: the
     writer does `str(value)`, which would send Python's `"True"`;
  3. the plan-creating action (`create-timeline`) holds no HubSpot client or deal id today: it would
     need the deal id, read from the child's HUBSPOT external reference (`children.listByChildIds`
     returns `externalSystemsReferences`), and an injected writer.
  The HubSpot property must be a single checkbox (boolean) or a text/dropdown that accepts those
  values; that is for Drew to confirm in HubSpot.

## Part B (2026-10-27). Parent app access and invoice recipients

Read-only: the public schema (412 types) and the internal schema (3931 types) with descriptions, from
the same introspection as above. Nothing was written. What the schema states is marked as stated;
what it only suggests is marked as inferred.

**How Famly gives a parent app access (stated).** Access is a ROLE on the contact for the child, and
a role needs a login:
- Public `ContactInput.roles: [RoleAssignmentInput {roleId, targetId}]` (targetId is the child; the
  role target type is CHILD): "If you add a roles to the contact which does not yet have a login, this
  will create a login for them." Supported role ids named in the schema: Parent
  (`d27c12e8-e1bf-4cb6-b10e-def7a83e3350`), Parent (limited access)
  (`d8632ad6-0b47-4479-8f1d-fcb0477ff4db`), Family (`2a8c1370-3ea7-40e8-9a60-8773bbe66c5e`).
- Public `contacts.update(roles: [ContactUpdateRoleId {contactId, roleId}])` is the single-field way
  to change a role on an existing contact (`roleId` is optional; that leaving it out clears the role
  is inferred from the "update just the roleId field" wording). The full `contacts:` update takes
  `roles: [RoleAssignmentInput]` and replaces them.
- Internal `childContacts.updateRole(relationId, role: {roleId!, newEmail})`: "If none provided, any
  roles or role invitations will be removed. If provided, the role will be assigned directly or a role
  invitation will be created." `newEmail` changes the contact's email first. A contact created through
  the internal `ContactInvitationInput` takes a `roleId` and creates an invitation the same way.
  `resendVerifiedInvitation(invitationId)` resends a pending one (rate limited).
- An invitation is verified by `DATE_OF_BIRTH`, `FULL_NAME` or `NO_VERIFICATION`
  (`RoleInvitationVerificationMethod`); `Contact.roleInvitations` lists pending ones.

**What a pipeline contact lacks for a login (stated, from the code and the schema).** Contacts are
created with `roles: []`, so they have no role assignment and no invitation, and therefore no login.
They do have an email, which an invitation needs. There is a mutation to grant it: the public create
with a role, or the public `contacts.update(roles: ...)` for an existing contact (one write per
contact, the same pattern as the RELATION update), with the Parent role id above. Which role the
nursery wants (Parent, or Parent (limited access)) and whether an invitation email goes out the moment
a role is added is a decision for Drew, not something the schema settles; granting a role may email the
parent, so it must sit behind Gate A and be clearly shown in the status block.

**Does adding an invoice recipient alone make invoices visible to that parent? Not by itself
(inferred).** The schema does not say what a recipient sees. What it does say points two ways:
- a recipient is a notification target: `BillPayer.canBeNotified` is true if the payer has an email or
  "an email is set on at least 1 of the invoice recipients"; so a recipient with an email can be told
  about an invoice without any login (inferred: by email);
- the parent-facing internal queries are written per signed-in user: "each bill payer the user is an
  invoice recipient for" (payment method restrictions) and "contact for the child, invoice recipient
  for the bill payer, and bill payer has shares" (Tax-Free Childcare). So seeing and paying invoices in
  the app depends on being a signed-in user who is a recipient AND whose bill payer has a share for the
  child. A contact with no login cannot be that user. The internal `InvoiceRecipient` also carries
  `showLimitedContactRoleWarning`, so the role of the recipient matters (a Parent (limited access)
  contact probably triggers a warning; inferred from the name).
So the app needs both the recipient link and a login role; the probe's test payer says nothing
about visibility either way. Only a test with a real login could settle this, and none is proposed.

**Is there a removeInvoiceRecipients? Not by that name.** The public mutation is
`billPayers.deleteInvoiceRecipients(invoiceRecipients: [InvoiceRecipientDeleteInput {relationId!,
billPayerId!}]) -> [InvoiceRecipientDeleteResult {billPayerId, relationId}]`. It needs BOTH ids, for
every pair; there is no "delete all of a payer's recipients". The internal API has no recipient
mutation at all (only the read `billPayers.invoiceRecipients(billPayerId)`).

**Where recipient linking fits in the bill payer stage (proposal, not built).** As in Part 6: a third
step of `bill_payer_writes.run_stage`, after the create or attach has been read back, for the bill
payer contact only.
- Plan time: add `invoiceRecipients { relationId billPayerId }` to the existing payer scan (no extra
  request) and set `billPayer.recipient` to `would_link`, `linked` or `contact_missing`, in the plan
  hash.
- Write: one `addInvoiceRecipients` {relationId: the contact id, billPayerId}, sent once, never
  retried, never for a pair already listed, never for a child-only stage.
- Settled by a live read: the payer scan again (bounded `LOOKUP_RETRY_WAITS`): the pair listed exactly
  once is done. If the probe shows a repeated add duplicates, the read is also the only protection
  against a second row, so an unknown outcome is settled by reading and NEVER by sending again; a
  pair not showing after the retries is a To check flag, not a stop.
- Gate A: counted as one write ("N bill payer contact link"), so a deal whose only missing piece is the
  link still asks for approval.
- Status block (`plan_status`, wording in `messages.state`): new lines under the bill payer line,
  "Bill payer: invoices will go to contact <id> (will be linked)", "...already linked", and a flagged
  line with the reason in words; the child-only line is unchanged.
- Separately and later: the parent login (a role grant) as its own plan field and its own status line,
  because it can send the parent an email.

The probe is `probe-invoice-recipient --child-id <TEST child> --confirm` (not run by Claude). Its
steps 3 and 4 answer whether the contact appears and whether a repeated add deduplicates; step 5
answers whether a contact with no reference can be given exactly one HUBSPOT reference through the
full update.
